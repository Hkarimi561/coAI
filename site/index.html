    3 · Knowledge ingestion into Qdrant

    Chunking: structure and logic, step by step

    chunk_markdown in chunker.py has two phases: Phase 1, parsing (line by line, building sections and blocks) and Phase 2, packing (placing each section’s blocks into chunks up to CHUNK_MAX_CHARS). This section is a port of the same algorithm and shows every step.

    Phase 1: each line is checked in this priority order
    
  
      
   
    1. Inside a fence? The line is appended to code. If it is the same fence character, at least as long, and the only content of the line, the code block is closed.
      2. 
   
    2. Line starts with ``` or ~~~? The current paragraph is flushed and “inside code” mode starts.
      3. 
   
    3. Heading # to ######? The previous section is closed; the stack is popped to the parent level and the new heading is pushed.
      4. 
   
    4. Blank line? The current paragraph is stored as a text block.
      5. 
   
    5. Otherwise the line is appended to para.
      6. 
  
    
  
    Result of phase 1: a list of sections; each = heading path + its text/code blocks.
    
 
    Phase 2: packing each section
    
  
      
   
    1. Each section is packed on its own: a chunk never crosses a heading boundary (small sections are not merged).
      2. 
   
    2. A text block longer than the limit is split line by line (_split_long_text); a code block is never split.
      3. 
   
    3. Each piece is appended to cur (joined by a blank line). If appending would exceed the limit, cur is emitted as a chunk and the piece starts the next one.
      4. 
   
    4. At the end of the section the remainder of cur is emitted. A section with only a heading and no body is never recorded in phase 1, so it makes no chunk (its heading still appears in the path of sub-sections).
      5. 
   
    5. Chunk heading: Doc title > H2 > H3 (a duplicate of the doc title is dropped).
      6. 
  
    

    


    Final output (click a chunk to see its payload)
    

    
 
    
  
    Split map
    One color per chunk; width = characters.
    
   
    Chunk count vs. max length
    
  
    
 
    
 
    

    


    
 
    No overlap
    Chunks do not overlap and the size unit is characters, not tokens. A 1400-character limit is conservative for e5-small (512-token maximum).
    
 
    Headings are part of the embedded text
    The model receives heading + "\n" + text, so a query can match the section name too. In the payload, text is only the chunk and heading is separate.
    
 
    Versioning and updates
    The point id is uuid5(path#index). On re-index, old chunks of that path are deleted and new ones upserted. If the file hash is unchanged and the point count matches, embeddings are not recomputed at all.
    
 
    MDX and front matter
    .mdx files first go through clean_mdx (drops import/export and PascalCase JSX tags, keeping their text). The title comes from front matter or the first H1 outside code.
    
 
    Oversized code
    A code block larger than the limit becomes a chunk by itself and is not cut; that chunk can exceed the limit.
    
 
    Limitations
    Very small sections make small chunks; long tables and lists are split line by line like plain text; cut quality depends on the document’s heading structure.

    6 · Redis and web search
    Single-flight lock: many askers, one search
    

    Run the WebSearchService.search algorithm: every caller checks the cache first; exactly one takes the lock and goes outside; the others poll the shared cache every 0.4 s (for up to 50 s).
    

    
 
    
  
    Simulator

    —without the lock
    —longest wait (seconds)
    
 
    
 
    
  
    cache check / lock attemptoutbound searchwaiting (poll every 0.4 s)resulterror
    

    

    
 
    Steps in code
    
 
      
  
    1. lookup(key): Redis first, then PostgreSQL (and if found there it is stored in Redis again).
      2. 
  
    2. If sf:err:key exists: fail immediately; a concurrent search just failed.
      3. 
  
    3. SET sf:lock:key token NX EX 45; only one caller succeeds.
      4. 
  
    4. The lock winner looks up again (double-checked locking), then calls the providers concurrently (GitHub + SearXNG).
      5. 
  
    5. The result is redacted, upserted into PostgreSQL, put in Redis and indexed in Qdrant (kind=web).
      6. 
  
    6. The lock is released with a Lua script: delete only if the value is still my token.
      7. 
  
    7. The others loop with asyncio.sleep(0.4) and receive the event coalesced.
      8.

    11 · Image processing
    Screenshots: from upload to answer
    

    Users can attach screenshots of an error (terminal output, a dashboard, a browser console). Every file is treated as untrusted input: it is validated, re-encoded and stored by services/images.py; then a vision model reads it so retrieval and web search can work from what the picture shows; finally the answer model sees the picture itself. Change the file below and watch which rule fires.
    


    
 
    
  
    Try an upload
    
  
  
  
  
  
  
    
   
   
   
  
    
 
    
 
    
  
    What the server does
    
  
      
  
      
 
      

      


      
 
      The whole path of one screenshot
      
 
      
 
      

      


      
 
      Two different uses of the image
      
  
        
   
      • 1 · Transcription call. One short vision request (READ_IMAGE_PROMPT, max 700 tokens) copies every error line, command, URL and status code visible in the picture. The text is passed through redact() (secrets and tokens are masked) and cut to 1,500 characters. Its first 500 characters are appended to the user’s message, so document search, the error signature and the web query “see” the screenshot.
        • 
   
      • 2 · Answer call. The answer model receives the real images again (OpenAI image_url or Ollama images), plus the transcription inside <untrusted_screenshot_text> and rule 13: describe what it shows, quote the exact error, and say so if the picture is unreadable.
        • 
   
      • If only an image is sent without text, a default request (“look at the attached screenshot, explain the problem, suggest a fix”) is used.
        • 
   
      • If LLM_VISION=false, no image is sent anywhere; the model is told to say it cannot see images and ask for the pasted error text.
        • 
  
      
 
      What the user sees
      
  
        
   
      • An attach button next to the message box; screenshots can also be pasted (Ctrl+V) or dragged into it.
        • 
   
      • Thumbnails appear above the box with a remove button. The browser pre-checks the limits (4 images, 8 MB each) before anything is uploaded.
        • 
   
      • On send, the conversation is created if needed, each file is uploaded to POST /chat/conversations/{id}/images, and the returned ids go with the message as image_ids.
        • 
   
      • While the server works the status line shows “Reading the attached image…”, then the usual search steps.
        • 
   
      • In the thread, thumbnails sit above the question and open full size in a lightbox; images are served by an authenticated endpoint with nosniff and a private cache header.
        • 
   
      • Answers about a screenshot are never replayed from the answer cache and never written to the web cache, because the same text with a different picture is a different question.
        • 
  
      

      


      
 
      Safety layers
      
  
      
   
      ThreatDefence
      
   
      Fake or malformed fileDecoded by Pillow; format must be PNG, JPEG, WebP or GIF, otherwise HTTP 400.
      
   
      Decompression bombMAX_IMAGE_PIXELS = 60 M; the upload size is read with a hard cap of limit + 1 bytes.
      
   
      Hidden payload, EXIF, GPSThe image is fully re-encoded from pixels (JPEG/WebP q88, PNG optimised); metadata and trailing data are not copied.
      
   
      Path traversalThe stored name is a random 32-hex id plus a fixed extension; lookups reject anything else. The user’s filename is only kept as a sanitised label (≤ 80 chars).
      
   
      Other users’ filesFiles live under uploads/<conversation>/; only the conversation owner can upload and the read endpoint checks ownership.
      
   
      AbuseRate limit of 60 uploads per minute per user.
      
   
      Secrets in the pictureTranscribed text is redacted before it is stored, searched or sent to the answer model.
      
   
      Prompt injection in the pictureThe vision prompt says never to follow instructions inside the image; the text is wrapped as untrusted data and its closing tag is neutralised.
      
  
      
 
      Settings (config.py)
      
  
      
   
      SettingDefaultMeaning
      
   
      LLM_VISIONtrueThe chat model can read images. Turn off for text-only models.
      
   
      MAX_IMAGE_MB8Largest accepted upload.
      
   
      MAX_IMAGES_PER_MESSAGE4Images per message (extra ones are rejected).
      
   
      IMAGE_MAX_SIDE1600 pxLongest side after downscaling (LANCZOS); smaller images are never enlarged.
      
   
      UPLOADS_DIR/data/uploadsWhere sanitised files are stored.
      
  
      
  
      The message itself stores only {id, name, ext, width, height, size} in its metadata, never the pixels. The admin conversation view shows the transcription that was extracted, which helps when an answer looks wrong.
